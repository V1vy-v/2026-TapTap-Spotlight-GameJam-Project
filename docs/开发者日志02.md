### 2.2 四条已拍板的关键决策

这四条直接决定架构，本期已确认：

| # | 决策 | 对开发的影响 |
|---|---|---|
| 1 | **2.5D 无纵深，Z 轴纯表现** | 所有判定（移动 / 命中 / 碰撞 / 视野）只在 XY 平面做；"前后"只用 Y 轴排序 + 缩放视差表现，不做 Z 轴命中，也不做前后闪避 |

### 2.3 全局规则定稿

- **操作总表**：WASD 移动 ｜ J 普攻 ｜ K 技能 ｜ Q 切换近/远战 ｜ Tab 切换液体形态 ｜ F 交互/吸取/兑换 ｜ 长按空格 喷射 ｜ 长按 X 倾倒 ｜ Esc 菜单 ｜ 鼠标悬停看道具功能。
- **液体槽**：共 2 格、无主副之分；未在使用中的称"备用槽"；最多携带 2 种液体。
- **切换**：冷却脱战 1 秒 / 战斗中 10 秒；两槽都必须是"可作主形态"的液体才生效（料酒、冰美式这类纯被动液体不能切为主形态）；有主动形态的液体不再提供备用槽被动。
- **吸取 / 倾倒**：吸取一般只对 BOSS 级有效（中三拳是剧情特例）；倾倒只能倒备用槽、需脱战、无冷却、无专门动作，液体永久失去。
- **敌人分级与掉落**：小怪 / 精英 / BOSS；精英掉 1 瓶盖，BOSS 掉 2 瓶盖且可吸取，其余不掉落；擂台胜利基础奖励 1 瓶盖。
- **出场机制（通用）**：精英与 BOSS 由"进入特定区域"触发，出场先播对话再开战；BOSS 战场地可以覆盖整段道路（如雷碧 = 整个下路）。
- **统一状态系统**：11 种状态由同一套 `StatusEffect` 承载，玩家与敌人共用——冰冻、红温、冰镇、涌动、酒雾、亡语、击杀增益、蓄力、速度增伤、减速、技能加速。
- **任务与引导**：只有主线、不可点击、没有任务窗口；左上角一行文字（在血条与道具栏下方）+ 场景内指向箭头 + 右上角常驻位置地图。

## 三、程序：Gameplay 框架搭建

本期的程序工作分两半：前半段（10-09 ~ 10-11）把渲染管线、输入、寻路、角色、敌人、对话、配置这些"零件"逐个打通；后半段（10-12 ~ 10-13）把它们组装进一套分层的框架里，并明确区分**全局流程**与**局内模式**。

### 3.1 分层与启动链路

代码分四层：`Core`（全局宿主）→ `Framework`（与玩法无关的通用框架）→ `GamePlay`（玩法层）→ `UI`（界面层）。业务层不直接引用 `AppCore`，而是通过服务定位器 `Global` 取子系统。

启动顺序（`AppCore.InitializeGameCore`）：

```
AppCoreConfig（帧率、YooAsset 播放模式、资源包名）
  └─ SystemManager
      └─ ResourceManager（YooAsset Provider，异步初始化资源包）
          └─ OnResourceReady
              ├─ InitSubSystems()：Instantiate / Pool / Timer / DataProxy /
              │                    UI / Scene / LocalInput / Audio / Camera / GameplayRoot
              ├─ InitDataProxy()
              └─ IsReady = true → OnAppReady 事件
```

有几个细节值得一提：

1. **资源优先**：`ResourceManager` 单独先注册并等它 `OnResourceReady`，其余子系统才逐个注册——避免子系统启动时资源还没就绪。
2. **`OnAppReady` 是"订阅即回调"的**（已经就绪后再订阅会立刻收到一次），订阅方不必关心 `Awake` 顺序。`ProcedureCore` 正是靠这个特性安全启动：它在自己的 `Init()` 里挂 `AppCore.OnAppReady += StartUp`，就绪后自动跳到主菜单。
3. **`GameplayRoot` 是被 `SystemManager` 注册的普通子系统**（优先级 -30），它的 `Update/FixedUpdate/LateUpdate` 与生命周期都统一走框架——10-09 时它曾有一个独立的 Mono 启动器 `Bootstrap/GameplayBootstrap.cs`，10-11 的"Gameplay 子系统转交 SystemManager 接管"把启动器删掉了，职责收归 `AppCore` + `ProcedureCore`。
4. **时间推进用非缩放时间**（`Time.unscaledDeltaTime` / `fixedUnscaledDeltaTime`），暂停不依赖 `Time.timeScale`；退出时先 `OnAppQuit`（业务侧拆对局），再 `SystemMgr.Destroy()` → `Global.Clear()` → `EventBus.Clear()`。

### 3.2 服务定位器与子系统顺序

`Global` 是静态门面：`Register/Get/TryGet`、`GetDataProxy`、`Load/LoadAsync`、`Instantiate/InstantiateAsync/InstantiateUnpooled/Release`、`LoadScene`、`ShowUI/HideUI/HideAllUI`、`QuitGame`。

子系统执行顺序由 `SubSystemPriority` 显式声明，避免隐式依赖：

```
SystemManager(Min) < Resource(-200) < Instantiate(-175) < Pool(-150) < Timer(-120)
  < DataProxy(-100) < LocalInput(-40) < GameplayRoot(-30) << UI(5000) < SceneLoader(6000)
  < Audio(7000) < Camera(10000)
```

`SystemManager` 的注册/注销也做得比较扎实：Tick 期间注册只打标记延迟排序，注销进待删列表并在 `EndTick` 按优先级逆序销毁，避免遍历中抽掉正在更新的系统。

### 3.3 两层状态机：全局流程 vs 局内模式

这是本期架构上最关键的一刀，也是本期最大的一次重构（10-13，102 个文件、+2,581/−4,785）。

**重构前**：`ProcedureState` 有 8 个状态——`Menu / Loading / FreeRoam / Dialogue / Cutscene / Battle / Pause / GameOver`，也就是把"场景加载"和"这一局里的战斗/对话/演出"全塞在同一个状态机里。

**重构后**：全局流程只保留三段，局内状态整体下移。

**外层 · 全局流程 `ProcedureCore`（MonoSingleton）**——负责"应用级"的阶段：

- 状态机 `StateMachine<ProcedureState>`，只注册 **Menu / Loading / Playing** 三态。
- 带**加载闸门**的切换：`RequestState(state, ILoadTask task)` —— 没有任务就立即切；有任务则先进 `Loading`，任务完成后进入目标状态。切换任务由 `ProcedureTransition` 显式持有（全流程同时只允许一个，加载中再次请求会停掉当前任务换成这一次）。
- `RequestPlay()` → `Playing` + 进 `GameScene`；`RequestMenu()` → `Menu` + 回 `MainScene`；场景加载失败走 `FailTransition()` 回菜单，不会卡在加载态。
- 任务实现目前只有一个 `SceneLoadTask`：切场景前先清场（清场景实例池 + 清未用资源 + 关掉所有 UI），再订阅 `SceneLoader` 的完成/失败事件。

**内层 · 局内模式 `GameplayRoot`（SubSystemBase）**——负责"这一局"内部的状态：

- 状态机 `StateMachine<GameplayMode>`，注册 **FreeRoam / Dialogue / Cutscene / Battle / Pause / GameOver** 六态（枚举定义在 `GameplayState.cs` 里）。
- 对局寿命：`StartNewGame()` 建 Session 上下文 + 从资源管线实例化玩家预制体（`Global.InstantiateUnpooled(GlobalConstants.PlayerPrefabLocation)`）；`EndGame()` 回收玩家、停状态机、清空上下文。
- 暂停只在 FreeRoam / Battle 下允许，`Resume()` 回到**暂停前**的模式（`_resumeMode`），而不是硬编码回 FreeRoam。
- 对业务暴露：`ChangeMode()` / `AdvanceNode()` / `AdvanceStage()` / `EnterBattle()` / `EndBattle()`。

**两层怎么衔接**：只有两个点——`ProcedurePlayingState.Enter()` 里 `GameplayRoot.StartNewGame()`（新档）或 `ContinueGame()`（读档）；`Exit()` 里 `GameplayRoot.EndGame()`。也就是说**"离开关卡的这条边"就是拆对局的地方**。`ProcedureStateBase` 给所有全局状态提供了 `protected GameplayRoot GameplayRoot => Global.Get<GameplayRoot>()` 的便捷访问，内层各状态只持有自己那一段的数据，不需要知道场景是怎么来的。

| | 全局流程控制 | Gameplay 流程控制 |
|---|---|---|
| 载体 | `ProcedureCore : MonoSingleton` | `GameplayRoot : SubSystemBase` |
| 状态 | Menu / Loading / Playing（3） | FreeRoam / Dialogue / Cutscene / Battle / Pause / GameOver（6） |
| 职责 | 跨场景、资源与 UI 清场、对局的开与关、加载闸门 | 单场景内的模式切换、剧情推进、玩家实例、Session 数据 |
| 启停 | 订阅 `AppCore.OnAppReady` / `OnAppQuit` | 由 `ProcedurePlayingState` 的 Enter/Exit 驱动 |
| 存活范围 | 全程 | 仅一次对局 |

框架侧是 `LocalInputManager` + `LocalInputProvider` + `InputState`，支持按场景切 ActionMap：菜单/对话/演出切到 `UI` Map，局内切回 `Player` Map（`GameplayModeStateBase` 用 `InputMap` 属性统一处理）。

**主角**：`Player.prefab` 已成型——Tag `Player`，`SpriteRenderer`（`player_default`）+ 重力 0 的 `Rigidbody2D` + 两个 `CapsuleCollider2D` 子物体（`MoveCollider` 实体碰撞 / `Hitbox` Trigger 判定），挂 `PlayerController` 与 `PlayerCombat`（后者带 `enemyLayerMask`）。

链路是通的但数值还没接：移动走 `Rigidbody2D.velocity = 输入 × moveSpeed` 已经成立，可 `PlayerStats` 是在 `Awake` 里 `new` 出来的普通 C# 对象、没有任何地方从配置赋值，所以 **`moveSpeed` 目前是 0**；战斗侧 `PlayerCombat.RangeAttack()` 的 `OverlapCircleAll` 命中检测跑得通，但循环体里还没有结算逻辑（不调 `EnemyController.ApplyDamage`），`PlayerWound()` / `DirectionalAttack()` / `SearchForEnemy()` 也还是空实现。所以本期的能力边界是：**能跑起来、能看见、按键有反应，但还打不死人**。

**敌人**：状态机是完整的——`EnemyController` + `EnemyStateBase` + 六个状态（Idle 待机 / Patrol 巡逻 / Chase 追击 / Attack 攻击 / Hurt 受击 / Dead 死亡）+ `EnemyDetectZone`（`Detect` / `Attack` 两种触发区，进范围置标志位，状态机据此切换，这也是"潜入与脱战"的基础）。

两处关键缺口：

1. **移动还没接上**：`EnemyChaseState` 里真正调用寻路的那行 `Enemy.MoveToTarget()` 目前是注释状态，`Patrol` 状态也没有任何移动调用；攻击状态只播动画、重置计时器，不造成伤害；死亡状态只做渐隐，没有回收。
2. **资产还没装配**：`enemy_test.prefab` 上只有 `EnemyController`，**没有 `EnemyMoveController`、没有 `EnemyDetectZone`、没有 `NavMeshAgent`、没有 `Animator`**；两个场景里也都没有 `NavMeshSurface`。也就是说 NavMeshPlus（2D 寻路）的**代码封装已完成，但场景与预制体尚未装配**——`EnemyController.Awake()` 会因为 `moveController == null` 直接 return（静默），敌人会在待机与巡逻之间空转。

**其它**：`Obstacle` 一族按文档 06 的三类障碍分好了（不可破坏 / 可破坏 / 可推动），但受击行为还是空接口；`Liquid` 有 `LiquidBase`（抽象液体）与 `Cola`（快乐水）两个骨架。

### 3.6 对话系统

`DialogController.cs` 里的控制器类叫 `DiaLogController`（注意那个大写的 L），搭配 `CharacterDatabase`（角色立绘库，类在 `CharacterDatabase_Dialog.cs` 里）与 `CharacterEntry`；界面是 `DialogPanel`（`RoleA` / `RoleB` / `BK` 三个立绘位 + `NameText` / `DialogText`）。

**两个待办**：① 对话文件必须放在 `Resources/` 下，而现在的示例文本还在 `Assets/Prefabs/Text/` 且是 `.txt`，`LoadDialogFile()` 现在必然报错；② `CharacterDatabase_Dialog.asset` 的脚本引用在工作区里损坏（`m_Script: {fileID: 0}`），Inspector 会显示 Missing Script，需要在 Unity 里重新绑定（不能手改 GUID）。另外 `DialogPanel` 上目前同时挂着新的 `UIView` 和旧的 `DiaLogController`，两套入口后续要二选一。

### 3.7 UI 框架与界面

界面按 `Binding/`（自动生成的控件引用）+ `Logic/`（界面逻辑，`partial class`）+ `Properties/`（对外参数）三层拆分；绑定代码由编辑器工具 `UIViewBindingEditor`（1055 行）在 Inspector 里生成，新增界面沿用这套拆分并保留 `// <ui-bind:add>` 标记块即可，不需要手写控件查找。这个工具还带了个很实用的保险：打包前校验所有 UI 预制体的脚本引用能否解析，有坏的直接中断打包，而不是等到真机上才发现界面起不来。

`UIManager.prefab` 里已经铺好完整层级：`PanelLayer`（下含 Priority / Tutorial / Blocker / None 四个子层）/ `WindowLayer` / `WindowPriorityLayer` / `SceneLayer` + `Canvas` + `EventSystem`；窗口层还带历史栈、排队、弹窗蒙黑，界面实例隐藏超过 30 秒会被自动回收。另有两套界面动画组件（`AnimationView` 用 Legacy `Animation`，`FadeAni` 用 `CanvasGroup` 淡入淡出）。

界面本身按"资源地址 = `UI_预制体名`"的约定加载（`Global.ShowUI("BeginPanel")` → `UI_BeginPanel`）。当前已有 6 个界面预制体，但**只有 `BeginPanel` 一套三层的脚本是齐的**（它的"开始"按钮已经接到 `ProcedureCore.RequestPlay()`，"设置"按钮调 `Global.ShowUI("SettingPanel")`）；`LoadingPanel`、`MainScenePanel`、`DialogPanel`、`SettingPanel` 的 Binding/Logic/Properties 还没生成，点了会报"找不到界面脚本"。此外 `MainScenePanel` 是从旧工程移植过来的模板（还是"本地 / 多人 / 主机"那套按钮），后续要重做成 HUD。所有界面的 `animIn` / `animOut` 也都还没配。

编辑器工具还有：对象池调试窗（`InstantiateManagerDebugWindow`，`Tools/Framework/Instantiate Pool`，实时看每个资源位置的借出/空闲/等待与内存）、Protobuf 编译窗（`ProtoCompilerWindow`，为将来联机协议预留，**目前未使用**）、以及把运行时日志显示到屏幕的 `ConsoleToScreen`。

## 五、音频制作

音频这一章要写得诚实：**链路已经完全打通、并用一个测试音效验证过"能出声"，但正片音频内容还没有开始制作**。工程里目前唯一的自制素材是一声狗叫。

### 5.1 工程与集成

- Wwise **2022.1.19.8584**，Unity 集成包 Integration 19；Wwise 作者工程在仓库根目录 `Taptap_Wwise/`，已纳入版本控制（67 个文件）。
- 工程产出路径已指向 Unity：`SoundBankPaths → Assets/StreamingAssets/Audio/GeneratedSoundBanks/Windows/`；`WwiseSettings.xml` 里 `CopySoundBanksAsPreBuildStep = true`（构建前自动拷贝 bank），WAAPI 端口 8081（供编辑器自动化与批量建 Event 用）。
- 平台只配了 Windows（若后续要出移动端需要补平台）。
- 验证链路用的端到端样本：Event `Play_Test_Sound` → Sound SFX `Test_Sound` → 素材 `狗叫1－xh20070511.wav`（0.82 秒、36 KB），打进 `main.bnk`（36,389 B）。

### 5.2 Unity 侧音频子系统

`AudioManager` 已经是标准子系统（优先级 7000，由 `AppCore` 注册），业务侧统一用 `Global.Get<AudioManager>()` 取用。它把 Wwise 包成了强类型接口，不散落字符串 ID：

| API | 用途 |
|---|---|
| `Play(key, emitter)` / `Stop(key, emitter, fadeMs)` | 按 key 播放 / 停止（key → `AK.Wwise.Event` 的字典来自配置） |
| `SetState` / `SetSwitch` / `SetRTPC` | 状态、开关、实时参数 |
| `ChangeMasterVolume` / `ChangeMusicVolume` / `ChangeSfxVolume` | 总线音量 |

`AudioConfig`（`Assets/Resources/AudioConfig.asset`）负责声明：要加载哪些 bank（含 `loadOnStart`）、Event 表（key → Event）、以及三个音量 RTPC。运行时 `AudioManager` 会创建一个常驻 `[AudioManager]` 对象（`DontDestroyOnLoad` + `AkGameObj`）承载非空间化播放；因为 Wwise 引擎初始化晚于 `AppCore`，bank 采用**延迟加载**：每次播放前先判 `AkSoundEngine.IsInitialized()`，就绪后才真正 `Bank.Load()`。

### 5.3 内容现状

| 项 | 现状 |
|---|---|
| Event | 1 个（`Play_Test_Sound`，测试用） |
| Sound SFX / 容器 | 1 个扁平 Sound，无 Actor-Mixer、无 Random/Sequence/Switch/Blend 容器 |
| 自制音频素材 | 1 个（35 KB 测试音效）；无 BGM、无脚步、无 UI 音、无环境音、无战斗音效 |
| SoundBank | 1 个用户 bank（`main`）+ 引擎 `Init` bank |
| Bus / 混音 | 只有默认 Master Audio Bus，无自定义 Bus、无 Effect |
| Switch / State / Trigger / 自定义 RTPC / Attenuation | 全部为 0（Work Unit 都是空骨架） |
| 业务代码调用 | 0 处——目前跑起来不会播放任何声音 |
| 音量控制 | API 已就绪，但 3 个音量 RTPC 尚未在 Wwise 里建好并绑定，暂时是空操作 |

另有两处工程卫生问题记在案：① `AudioConfig` 里第一个 Event 的 key 写成了 `Test_Sound`（声源名）而实际 Event 是 `Play_Test_Sound`，命名要统一；② `Taptap_Wwise/GeneratedSoundBanks/Windows/` 里残留的是更早一版（Event 名 `Play_Waterfall`，且已不存在于工程源文件）的产物，**权威产物在 `Assets/StreamingAssets/Audio/GeneratedSoundBanks/`**，前者建议清理以免误导。

### 5.4 下一阶段的音频排期

按照已定稿的策划案，音频需要覆盖的面其实不小，已经整理成清单，等 M1 竖切跑顺就开工：
